This is the lever that matters for latency. Measured on this gateway, the same prompt took 18s at 1,200 output tokens, 27s at 4,000 and 58s at 8,000 — while every gateway stage together took 1.3ms. Effort is the second lever (low is ~25% faster than medium for a comparable answer), and the model tier is the third. Nothing in the gateway is worth switching off to go faster; see /health for the switches that exist and what they actually cost.
Reasoning models bill hidden reasoning against the same output budget, and on demanding work they spend far more of it than you would expect: measured on one heavy review prompt, gpt-5 used 1,937 tokens at low effort and 6,080 at high, claude-opus-5 2,828 and 3,886 — before a single visible character. Under ~3,000 the answer usually comes back empty on both vendors. The gateway warns before the call and flags it after.

    How a multi-agent system uses this gateway

    Your orchestrator does not pick models. It describes each unit of work and sends it with model:"auto"; the gateway routes each one independently. The two shapes below are where that pays — narrow jobs land on small models while the hard step gets a big one, and you never hand-maintain that mapping.

    Fan-out — scatter only

    orchestrator │ ┌────┼────┬────┐ ▼ ▼ ▼ ▼ A A A A N sub-agents, │ │ │ │ one shared prefix ▼ ▼ ▼ ▼ results used separately

    Fan-in — scatter, then gather

    orchestrator │ ┌────┼────┐ ▼ ▼ ▼ A B C workers → cheap models │ │ │ └────┼────┘ ▼ synthesiser sees everything at once

    Fan-out — the cache pilot

    1. N sub-agents fire in parallel against one shared prefix.
    2. A cache entry is only readable once the first response starts, so without help all N pay a cold write.
    3. The gateway makes one the pilot; the rest wait briefly, then read the cache it wrote.
    Each agent gets its own question about the same diff, so the six answers are worth comparing side by side. Leave this empty and every agent receives the identical prompt instead — which is what made them all look the same.
    Run enabled, then disabled, and compare total writes.

    Fan-in — scatter then gather

    1. Each subtask is routed on its own merits — narrow jobs get small models, a review-shaped one escalates by itself.
    2. Workers run in parallel; wall clock is the slowest one.
    3. The synthesiser sees every worker's output at once and is routed separately, usually to a larger tier.

    Latency baselines — what the colours mean

    Every band on the pipeline is measured against one of these segments. A colour you cannot check is a colour you have to trust blindly, so the mean, σ, percentiles, sample count and the exact ms threshold for warn and critical are all published here and at /admin/baselines. Segments under the sample floor report learning and are drawn neutral — mean and σ over a handful of points are noise, and colouring them would teach you to ignore the colour.
    Segmentnmean σp50p95 bestwarn ≥critical ≥ State
    Send a few queries — baselines are learned from your own traffic.
    Latency is right-skewed, so “2σ” does not mean “the slowest 2.3%” the way it would for a normal distribution — in practice it flags somewhat more. The bands are still computed in σ because that is the agreed vocabulary; p50 and p95 are shown beside the mean so the skew is visible rather than implied.
